### <a name="_qmphm5d6rvi3"></a>**Решение**

Выбрана архитектурная схема **Варианта Б (Хореография событий)**. Компоненты Edge-кластера независимы и взаимодействуют через локальный RabbitMQ, используя Mosquitto для изоляции промышленного слоя.

**Обоснование технологического стека:**
*   **Шина данных (RabbitMQ):** Конфигурация Topic Exchange обеспечивает гибкую маршрутизацию (маски топиков) и высокую живучесть компонентов.
*   **Изоляция (Mosquitto):** Выделенный MQTT-брокер разгружает основной шлюз от поддержания множества Modbus-соединений.
*   **Локальное API (Python + FastAPI):** Обеспечивает работу консоли дежурного и управление локальными настройками в условиях отсутствия внешней сети.
*   **Синхронизация (Platform Bridge):** Гарантирует целостность данных в центральном облаке после восстановления связи.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

**Альтернатива: Вариант А (API-First с gRPC-агентом)**
Локальная БД и брокер отсутствуют, данные стримятся в облако через легкий агент.
*   *Почему отвергнуто:* Критическая зависимость от интернета. Сложность реализации надежного буфера на стороне агента. Рекомендовано только для малых объектов с жестким лимитом бюджета на HW.

**Недостатки, ограничения, риски**

*   **Сложность отладки (Distributed Tracing):** Трудность отслеживания пути в асинхронной среде. 
    *   *Меры:* Внедрение сквозного Correlation ID во все сообщения и логи.
*   **Конкурентные события (Race Conditions):** Риск неверного порядка обработки команд. 
    *   *Меры:* Использование монотонно растущих Timestamp в заголовках AMQP-сообщений.
*   **Ресурсоемкость:** Вариант Б требует от 2-4 Гб RAM на Edge-сервере (Erlang, PostgreSQL, Python). 
    *   *Меры:* Тщательный сайзинг оборудования перед развертыванием.
*   **Переполнение диска:** Риск забивания памяти логами в долгое отсутствие сети. 
    *   *Меры:* Реализация кольцевого буфера (Circular Buffer) с приоритетом для критических алертов.
