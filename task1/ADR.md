### <a name="_3bfxc9a45514"></a>**Функциональные требования**
|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Система, Оператор | Выявление аномалий в поведении | Система анализирует видео в реальном времени; при обнаружении драки или задавливания немедленно (до 5 сек) отправляет алерт оператору. |
| 2 | Дежурный на ферме | Локальное оповещение при обрыве связи | В случае падения интернета, система формирует локальный сигнал для дежурного на ферме. |
| 3 | Система, Оборудование | Управление кормлением | Система рассчитывает и отправляет команды управления дозировкой на исполнительные устройства разных вендоров. |
| 4 | Система, ERP (1С:Агро) | Учет поголовья и кормов | Система периодически пересчитывает животных, прогнозирует расход запасов и синхронизирует эти метрики с центральной ERP. |
| 5 | Зоотехник / Система | Мониторинг здоровья и среды | Система оценивает внешние признаки болезней и собирает телеметрию с фильтров воды, предоставляя сводный отчет. |
| 6 | Платформа (Веб/Мобайл) | Предоставление API | Система отдает данные по метрикам и инцидентам для отображения в существующих или новых пользовательских интерфейсах. |

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**
|**№**|**Требование**|
| :-: | :- |
| 1 | **Отказоустойчивость:** Центральная система должна обеспечивать доступность на уровне 99,95%. |
| 2 | **Производительность видеоаналитики:** Время реакции нейросетевых моделей на Edge-устройствах должно составлять миллисекунды. |
| 3 | **Скорость оповещения:** От момента фиксации нештатной ситуации до доставки алерта должно пройти не более 5 секунд. |
| 4 | **Автономность:** Агенты на фермах обязаны продолжать работу при отсутствии интернета, с буферизацией данных. |
| 5 | **Синхронизация данных:** После восстановления связи допускается задержка синхронизации до 10 минут. |
| 6 | **Расширяемость:** Добавление новых метрик не должно требовать переписывания базового ядра системы. |
### <a name="_qmphm5d6rvi3"></a>**Решение**
В качестве основного подхода выбрана модель **«Модульного бэкенда (API-First)»**, где новая система выступает в роли "headless" провайдера бизнес-логики и данных, полностью делегируя пользовательский интерфейс существующим решениям платформы "АгроПром Х".

```plantuml
@startuml Архитектура_АгроТех_Решение_А
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Context.puml

title Решение А: API-First интеграция с платформой "АгроПром Х"

Person(директор, "Зоотехник / Директор")
Person(оператор, "Диспетчер")
Person(дежурный, "Дежурный на ферме")

System_Boundary(agro_platform, "Платформа 'АгроПром Х'") {
    System_Ext(веб_портал, "Веб-портал (React)")
    System_Ext(мобильное_приложение, "Мобильное приложение (Flutter)")
    System_Ext(kafka, "Apache Kafka", "Центральная шина")
    System_Ext(erp, "ERP (1С:Агро)")
}

System(livestock_system, "Система мониторинга животноводства", "Централизованный сбор метрик, агрегация данных с ферм, API для UI")

System_Boundary(farm, "Оборудование Фермы") {
    System_Ext(cameras, "Камеры")
    System_Ext(feeders, "Кормушки/Поилки")
}

Rel(директор, веб_портал, "Аналитика и дашборды")
Rel(оператор, веб_портал, "Онлайн мониторинг")
Rel(оператор, мобильное_приложение, "Алерты")
Rel(веб_портал, livestock_system, "REST/GraphQL", "API метрик")
Rel(мобильное_приложение, livestock_system, "REST/WebSocket", "API и алерты")
Rel(cameras, livestock_system, "RTSP/События")
Rel(livestock_system, feeders, "Управляющие команды")
Rel(livestock_system, дежурный, "Локальные алерты (Оффлайн)")
Rel(livestock_system, kafka, "События и метрики", "Kafka Protocol")
Rel(livestock_system, erp, "Прогнозы и поголовье", "REST")
@enduml
```

**Логика принятия решения:**
1. **Единое окно для пользователей:** Использование портала "АгроПром Х" снижает сопротивление пользователей и затраты на обучение.
2. **Изоляция бизнес-логики:** Выделение мониторинга в отдельную систему позволяет соблюдать принципы чистой архитектуры и развивать продукт независимо.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### **Решение Б: Standalone Платформа**
Создание полностью независимой системы с собственными интерфейсами (Веб и Мобильное приложение), которая интегрируется с "АгроПром Х" только фоновым обменом данных.

```plantuml
@startuml Архитектура_АгроТех_Решение_Б

!include https://raw.githubusercontent.com/RicardoNiepel/C4-PlantUML/master/C4_Component.puml

title Решение Б: Standalone платформа (Независимый продукт)

Person(директор, "Зоотехник / Директор")
Person(оператор, "Диспетчер")
Person(дежурный, "Дежурный на ферме")

System_Boundary(agro_platform, "Платформа 'АгроПром Х'") {
    System_Ext(веб_портал_old, "Старый Веб-портал")
    System_Ext(kafka, "Apache Kafka")
    System_Ext(erp, "ERP (1С:Агро)")
}

System_Boundary(new_product, "Продукт: Умная Ферма") {
    System(livestock_portal, "Livestock Web Portal", "Новый UI для зоотехников")
    System(livestock_mobile, "Livestock Mobile App", "Новое приложение для диспетчеров")
    System(livestock_system, "Ядро системы мониторинга", "Edge-аналитика и обработка данных")
}

System_Boundary(farm, "Оборудование Фермы") {
    System_Ext(cameras, "Камеры")
    System_Ext(feeders, "Кормушки/Поилки")
}
Rel(директор, livestock_portal, "Использует")
Rel(оператор, livestock_mobile, "Использует")
Rel(оператор, livestock_portal, "Использует")
Rel(livestock_portal, livestock_system, "API")
Rel(livestock_mobile, livestock_system, "API")
Rel(cameras, livestock_system, "RTSP/События")
Rel(livestock_system, feeders, "Управляющие команды")
Rel(livestock_system, дежурный, "Локальные алерты")
Rel(livestock_system, kafka, "Экспорт сырых метрик")
Rel(livestock_system, erp, "Экспорт финансовых показателей")

@enduml
```
**Логика альтернативы:** Оправдано, если планируется продажа системы как White-label продукта (SaaS) для хозяйств без существующей инфраструктуры.

**Недостатки, ограничения, риски**

*   **Риск "бутылочного горлышка" в UI-командах:** Зависимость от бэклога команд React/Flutter текущей платформы может замедлить релиз.
*   **Сложность авторизации (Ограничение):** Требуется SSO интеграция. В оффлайн-режиме проверка прав доступа усложняется без связи с центральным IAM.
*   **Жесткие требования к контрактам (API):** Любые изменения в структуре данных требуют строгой обратной совместимости, чтобы не нарушить работу дашбордов.
